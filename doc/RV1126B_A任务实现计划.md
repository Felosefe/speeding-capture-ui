# RV1126B Qt A 任务实现计划

版本：v1.0
日期：2026-07-20
负责人方向：软件 A，协议、设备连接与板端 HTTP/UDP 接入
适用工程：`D:\CameraManagerApp`，当前基线分支 `part-b`

## 1. 目标与边界

本计划实现 A 侧正式网络闭环：

```text
UDP 广播发现 -> 校验响应与设备去重 -> DeviceSession health 认证
                                          -> BoardApiClient HTTP 请求
                                          -> B: 事件同步 / 图片缓存 / FTP 快照
                                          -> C: 设备、配置、FTP 页面
```

本计划对应任务清单中的：

- `BAS-01` 协议基线和测试夹具。
- `BAS-02` 网络依赖与模块边界收口。
- `NET-01` 通用 `BoardApiClient`。
- `NET-02` `DeviceDiscoveryService`。
- `NET-03` `DeviceSession`。
- `NET-04` 展示配置与时间接口。
- `NET-05` FTP API 服务层。
- `SYS-02` 安全与诊断日志。
- `TST-01` 网络契约自动化测试。

不在 A 侧实现：SQLite、事件写入、图片的 JPEG 校验与正式文件提升（B 负责）；RTSP、窗口和页面逻辑（C 负责）；板端算法、FTP uploader 或板端文件路径处理（外部板端团队负责）。

## 2. 当前基线与结论

已具备：

- `Qt6::Network` 已加入工程。
- 协议 DTO、领域模型以及 `IBoardApiClient`、`IApiCodec`、`DeviceDiscoveryService`、`DeviceSession`、`FtpService`、`ISecretStore` 抽象接口已冻结。
- B 已完成 `BoardEventSyncService`、`BoardEvidenceCache` 等实现，它们只等待真实 `IBoardApiClient`。
- 板端 v1 HTTP/UDP 契约和真机端接口已冻结，默认 HTTP/UDP 端口分别为 `18080`、`18081`。

尚未实现：

- `IApiCodec` 的具体 JSON 编解码器。
- 真实 `IBoardApiClient`、UDP 发现、会话状态机、Windows Credential Manager 存储和 FTP 服务封装。
- A 侧协议夹具、网络自动化测试、安全日志和真机验证记录。

因此 A 应先完成可被 B/C 直接注入的底层服务，最后再做应用装配与真机联调；不能让 UI 直接操作 `QNetworkReply`。

## 3. 实现原则

1. HTTP base URL 只能来自发现响应或人工批准的设备配置；事件返回路径只接受同 scheme、host、port 且位于 `/api/v1` 下的相对 URL。
2. 所有 HTTP 请求使用 `Authorization: Bearer <token>`；Token 不进入 URL、日志、DTO、数据库、QSettings、测试夹具或断言输出。
3. JSON 请求使用 3 秒连接/首响应超时和 10 秒总超时；图片下载使用独立、可配置的总超时。所有 reply 均可取消。
4. 仅按稳定 `error.code` 和 HTTP 状态分类，用户层不得依赖 `message` 英文文本。
5. 响应忽略未知字段，已知必填字段缺失或类型错误返回 `Protocol` 错误。
6. UDP 不携带 Token；每次扫描的新 nonce 必须为 1 至 64 字节，响应同时校验 `magic`、`version`、`type` 和 nonce，并按 `device_id` 去重。
7. `401` 进入认证失败且不自动重试；网络错误/5xx 进入退化状态并按 1、2、4、8、16、30 秒退避；取消不报作网络故障。
8. FTP 密码仅以 `SecretValue` 短暂进入请求体；读取配置时只处理 `password_configured`，绝不回显密码。

## 5. 分阶段执行计划

### A1. 协议基线、夹具和 `BoardApiCodec`

对应：`BAS-01`。

实施内容：

- 根据 `RV1126B 应用接入 API.md` 固化 health、事件页/详情、evidence 配置、时间、FTP 配置/control/task 与 UDP 发现的合法 JSON 夹具。
- 同时提供缺失字段、错误字段类型、错误 JSON、未知字段、401/403/404/409/5xx 的无秘密夹具。
- 实现 `IApiCodec`：完整解析 `NormalizedTime` 和 `WireEnum`，保留 `rawJson` 与未知枚举原值。
- 实现所有请求 DTO 编码与输入校验：展示配置文本长度/控制字符、时间范围、FTP IPv4/端口/最多 8 个目标、密码 action、任务 UTC `[start,end)` 范围。
- 建立 `error.code -> ApiErrorCategory/retryable` 映射；错误信息不得回显响应中的秘密字段。

验收：

- 文档内所有正常 JSON 可解析、编码后字段名和类型与 v1 契约一致。
- 未知字段被忽略；必填字段缺失或类型错误得到 `Protocol` 错误。
- Token/密码不出现在任一夹具或解析失败文本中。

### A2. `BoardApiClient` 与 Windows 凭据存储

对应：`BAS-02`、`NET-01`、`SYS-02`。

实施内容：

- 实现 `WindowsCredentialStore`，使用 Credential Manager，credential target 固定为 `RV1126B/<device_id>`；`DeviceProfile` 仅保存 credential reference。
- 实现 `BoardApiClient`，由 `DeviceProfile`、`ISecretStore`、`IApiCodec` 构造并实现所有 `IBoardApiClient` 方法。
- 对 JSON 端点统一设置 Header、Bearer、`application/json`、请求体、超时与 reply 生命周期；处理 context 销毁、显式 `cancel` 和 `cancelAll`。
- 图片端点只把响应字节写入 B 指定的 `.part` 路径；检查 HTTP 200、`image/jpeg` 与 Content-Length，返回接收字节数，不负责 JPEG 解码或正式文件 rename。
- 严格解析非 2xx 响应的统一错误对象；连接/超时/取消分别映射 Network、Temporary、Cancelled。
- 对详情与图片相对 URL 做 base URL 同源及 `/api/v1` 路径检查，拒绝跨主机、跨端口和绝对板端路径。
- 加入脱敏诊断：仅记录操作名、device id、耗时、HTTP 状态和 error code，明确排除 Authorization、Token、密码、完整请求体和 URL query 中的秘密。

验收：

- B 可将 `BoardApiClient` 注入事件同步和图片缓存，无需自行拼 URL。
- 取消或 context 销毁后 completion 最多触发一次，reply 不泄漏。
- 401、403、404、409、5xx、网络超时和取消返回稳定分类。
- 日志与测试快照中不存在 Token、`Authorization` 或 FTP 密码。

### A3. UDP 发现与设备会话

对应：`NET-02`、`NET-03`。

实施内容：

- 实现 `UdpDeviceDiscoveryService`：枚举启用、非 loopback 的 IPv4 网卡及其广播地址；向每个适用子网发送一次不超过 1023 字节的 discover JSON。
- 每一次扫描使用独立 socket、scan id 与 nonce；在 1500 ms 窗口内处理数据报，并按 device id 去重后发出 `deviceFound`。
- 使用 `BoardApiCodec` 校验响应，忽略 magic/version/type/nonce 不符、格式不合法或 API URL 不安全的响应；取消后关闭 socket、停止定时器且不再发信号。
- 实现 `BoardDeviceSession`：连接时通过 health 校验 Bearer Token、health `device_id` 与 profile 一致；正确状态流转为 Connecting/Online/Degraded/AuthenticationFailed/Disconnected。
- `401` 进入 AuthenticationFailed 且停止自动重试；网络/5xx 进入 Degraded 并指数退避 health；重新发现同一 `device_id` 时只更新 endpoint，不新建身份。
- 评估 C 已完成的应用装配方式；若其需要 `DeviceFleetService` 具体实现，则以 `BoardDeviceSession` 为单会话单元实现最多 8 个数据会话的 fleet 适配层，而不让 UI 自行管理会话。

验收：

- 模拟 UDP 响应可校验 nonce、按 `device_id` 去重、取消无后续信号。
- health 成功且身份匹配才为 Online；错误 Token 为 AuthenticationFailed；网络失败后为 Degraded 并恢复。
- IP 变化后同一 device id 的本地设备身份和数据仍可继续使用。

### A4. 展示配置、时间和 FTP 服务层

对应：`NET-04`、`NET-05`。

实施内容：

- 通过 `BoardApiClient` 完成 evidence config 的 GET/PUT、time 的 GET/PUT，严格复用 codec 校验和错误映射。
- 实现 `BoardFtpService` 并完整实现 `FtpService`：config GET/PUT/rollback、control GET/PUT、task create/list/detail/retry。
- `saveConfigAndEnableNewEvents` 串行执行：先 PUT config，成功后使用响应 revision PUT control（`enabled=true`、`scope=new_events_only`）。第二步失败时返回 `configSaved=true, autoEnabled=false`，绝不伪装为整体成功。
- 409 revision conflict 原样保留为 Conflict，要求上层重新读取配置后由用户确认合并；不自动覆盖。
- 将 FTP task detail/page DTO 交给 B 的 `BoardFtpTaskSnapshotService` 持久化，由 C 展示；A 不直接写 SQLite。

验收：

- 返回配置不含密码，replace/keep/clear 请求符合契约。
- revision 冲突、写开关关闭和任务重试失败均有稳定 `error.code`。
- 配置成功但 control 失败可被 C 明确展示为“部分成功”。

### A5. 自动化测试、复查与真机准备

对应：`TST-01`、`SYS-02`。

新增测试：

- `ApiCodecTest`：全部 DTO、未知字段、畸形 JSON、枚举/时间、请求边界和脱敏。
- `BoardApiClientTest`：本地测试 HTTP 服务覆盖 Bearer、路径约束、200、401、403、404、409、5xx、JSON 超时、图片 Content-Length、取消及 context 销毁。
- `UdpDeviceDiscoveryServiceTest`：nonce、magic/version/type 校验、重复设备、超时和取消。
- `BoardDeviceSessionTest`：身份匹配、401 无重试、退化与退避恢复、endpoint 更新。
- `BoardFtpServiceTest`：两步启用、部分成功、revision conflict、分页、retry 与密码不回显。
- `WindowsCredentialStoreTest`：使用独立测试 target，验证创建/读取/删除和 target 命名；测试结束清理测试凭据。
- 日志脱敏测试：断言 token、Authorization 和 FTP password 不会出现于收集到的诊断文本。

真机准备材料：

- 设备 id、板端版本、IPv4、HTTP/UDP 端口、RTSP 地址、Token 的安全交付方式。
- 写开关状态：`APP_API_CONFIG_WRITE_ENABLED`、`APP_API_TIME_SET_ENABLED`、`APP_API_FTP_WRITE_ENABLED`、`APP_API_FTP_TASK_ENABLED`。
- 两个 FTP 测试目标及其中一个可控离线条件。
- 每个场景记录请求类别、预期 error code、实际结果、板端版本和脱敏日志。

验收：

- A 侧测试在无真机环境全部通过。
- 代码经 B 或 C 评审，完成接口与安全复查。
- 之后才进入三人 `INT-01`、`INT-02`、`INT-03` 真机联调。

## 6. 推荐执行顺序与阶段出口

1. A1：先完成 codec 和夹具，作为 HTTP/UDP 的唯一协议真相来源。
2. A2：实现凭据存储和 BoardApiClient，优先打通 health、事件、详情与 evidence 下载，以解除 B 的联调阻塞。
3. A5（第一批）：为 A1/A2 写协议和 HTTP 测试。
4. A3：实现 UDP 发现与 DeviceSession，使 C 可接入搜索和连接。
5. A4：实现配置、时间与 FTP 服务，并接入 B 的任务快照桥。
6. A5（第二批）：完成发现、会话、FTP、安全测试与真机清单。
7. 三人共同：执行最小真机闭环、FTP 故障联调、断线/IP 变化和长稳验证。

阶段出口：

- G-A1：codec 夹具测试通过，DTO 编解码可作为 A/B/C 共用协议基线。
- G-A2：B 能通过真实 `IBoardApiClient` 发起 health、事件和图片请求；无 UI 直接访问 reply。
- G-A3：C 能使用 discovery/session 显示设备与明确认证状态。
- G-A4：C 能使用配置、时间、FTP service；B 能持久化 FTP 任务快照。
- G-A5：A 侧自动化测试、脱敏复查和真机前检查完成。

## 7. 风险与外部依赖

| 风险/依赖 | 影响 | 处理方式 |
| --- | --- | --- |
| Token 或联调板不可用 | 无法验证真实认证与 health | 先以本地测试服务器完成 A1/A2；Token 仅通过安全渠道交付 |
| 写开关未开启 | 配置、校时、FTP 成功路径不可验收 | 覆盖 403；标记为外部依赖，不能伪造成功 |
| UDP 广播受 Windows 防火墙/网卡策略限制 | 发现功能看似无设备 | 提供网卡、广播地址、端口与收包日志，不退回依赖固定 IP |
| 纯 HTTP 明文传输 | 局域网凭据泄露风险 | 仅受控 LAN；发布说明明确限制；日志严禁秘密 |
| A/C UI 装配契约不一致 | 连接/状态重复管理 | A 实现服务，C 只消费状态；公共接口变更必须三方评审 |
| FTP revision conflict | 误覆盖现场配置 | 409 后重新 GET，要求用户确认，不自动覆盖 |

## 8. 完成定义

A 的每项任务完成前必须同时满足：

1. 实现位于 A 的协议/网络/会话/安全模块，B/C 不需绕过抽象接口。
2. 正常、错误、超时、取消和断开路径明确且不会重复回调或堆积请求。
3. 新逻辑有无秘密夹具和自动化测试；无法自动化的真机场景有可重复步骤。
4. Token、Authorization、FTP 密码、板端绝对路径不出现在 Git、SQLite、QSettings、日志或测试输出。
5. 至少由 B 或 C 进行一次代码评审，再合入共享分支。
