## 1. 结论与范围

本轮工作的核心不是继续开发板端算法或服务，而是在现有 Qt 工程上完成一条可靠的应用端闭环：

```text
发现设备 -> 认证连接 -> RTSP 预览 -> HTTP 事件同步
         -> SQLite 持久化 -> evidence 图片缓存与历史回看
         -> 展示/时间配置 -> FTP 自动与手动任务管理
         -> 断线恢复、资源释放、真机验收
```

板端 UDP 发现、HTTP API、事件查询、融合图下载、FTP 配置及任务已经通过主机集成测试和
RV1126B 真机验证。软件团队应按冻结的 v1 契约实现客户端，不重复实现板端事件生成、OCR、
融合图渲染或 FTP uploader。

### 1.1 当前 Qt 仓库可复用内容

- C++17、Qt 6 Widgets、Qt SQL、Qt Test 和 CMake 工程骨架。
- 主界面、设备列表、属性表、抓拍列表和系统设置界面。
- `MockDeviceClient`、`DeviceManager` 及模拟抓拍流程。
- `CaptureRecordService` 的 SQLite 基础能力。
- `CaptureStorageService` 的目录、清理和配置基础。
- `VideoWidget` 的界面占位和模拟画面。

### 1.2 需要改造或新增的关键点

- 工程尚未接入 `Qt6::Network`，也没有真实 UDP/HTTP 实现。
- 当前设备端口默认值和设备接口仍是模拟设备语义，需要增加真实 RV1126B 会话，不能把
  HTTP 的无状态访问模拟成板端“登录”。
- 当前抓拍主键是单一字符串；正式数据必须以
  `(device_id, event_id, track_id)` 为唯一键，并支持同一事件状态 upsert。
- 当前抓拍时间结构不能保存 `source_epoch_ms`、`offset_applied_ms` 和 `quality`，需要迁移。
- 当前存储服务创建的是空占位文件，不能作为 evidence JPEG 缓存实现。
- 当前 `VideoWidget` 只绘制模拟道路，需要接入经过验证的 RTSP 解码和重连链路。
- 尚缺 FTP 配置、自动下发、历史任务、任务状态和失败重试界面。

## 2. 软件与外部团队边界

### 2.1 三人软件团队负责

- Windows Qt 客户端的网络、数据、视频、界面和本地存储实现。
- 严格按 v1 契约解析响应、映射 `error.code`、处理超时和重试。
- Token 引用和 FTP 密码的安全输入、内存使用及日志脱敏。
- 单元测试、协议夹具测试、真机端到端测试、稳定性测试和发布材料。
- 对外部团队的问题提供可复现请求、响应、时间和日志，但不直接修改板端内部文件。

### 2.2 外部硬件/板端团队负责

- 提供已启用 App API 的联调板、`device_id`、设备型号和安全交付的 Bearer Token。
- 提供稳定 RTSP 主/辅码流、可触发事件的测试条件和最终 production profile。
- 按验收需要开启 `APP_API_ENABLED` 及经过批准的写开关。
- 处理板端时间持久化、厂商 `+8h` 时间链和整板开机自启动所有权问题。
- 确认板端事件保留策略，并在需要时补充 discovery `capabilities`。
- 配合提供板端日志和进程状态，定位只可能发生在板端的问题。

### 2.3 明确不做或不能假定的事项

- Qt 断开只释放 PC 资源，不停止 rkipc、OCR Worker、FTP uploader 或 App API。
- Qt 不读取 `/userdata/...`，不拼接板端路径，不执行板端 shell 命令。
- Qt 不自行固定减 8 小时；协议时间按 UTC epoch 毫秒保存，显示层再转换时区。
- v1 手动 FTP 任务只支持时间范围，不能用极窄时间范围模拟“任意勾选事件下发”。
- FTP 故障不能阻塞 HTTP 事件展示、本地入库或图片缓存。
- discovery 当前未声明 FTP/配置/时间能力，不能仅因 `capabilities` 缺少这些值就隐藏功能。
- 板端长期离线事件若已超过板端保留期，当前协议无法保证 PC 后续补齐。

### 4.1 模块协作约定

1. A 只向上暴露结构化结果和稳定错误码，UI 不直接操作 `QNetworkReply`。
2. B 只通过 `BoardApiClient` 获取数据，不在仓储层自行拼 HTTP URL。
3. C 通过 service/controller 组合功能，UI 不直接写 SQL、拼 FTP 命令或推断板端路径。
4. 共享 DTO 变更需要三人评审；每个 DTO 明确所有者，避免三条分支重复定义。
5. Mock 设备和协议夹具继续保留，用于没有真机时开发和 CI；Mock 行为必须服从 v1 状态模型。
6. 每项任务至少由一名非主责成员评审，合入前必须带对应测试或可复现验证步骤。

## 6. 最小端到端验收清单

以下 12 项直接作为交付门禁，不得仅以模拟数据通过代替真机结果：

| 编号 | 验收场景 | 通过标准 |
| ---: | --- | --- |
| 1 | 未知 IP 发现设备 | 对每个适用子网广播，校验 nonce/magic/version，按 `device_id` 去重并连接正确设备 |
| 2 | HTTP 认证 | 错误 Token 停止无限重试并提示；正确 Token 读取 health 且身份一致 |
| 3 | RTSP 与 HTTP 并行 | 视频持续播放时 health 和事件请求正常，任一链路故障不错误关闭另一链路 |
| 4 | 无 FTP 的事件闭环 | 新事件进入列表、SQLite 和 PC evidence 缓存，FTP 未配置不造成阻塞 |
| 5 | OCR 状态更新 | 同一复合身份从 queued 更新为终态，数据库和界面均只有一条记录 |
| 6 | 断线补齐 | Qt 离线期间产生的仍在板端保留期内的事件，重连后通过分页补齐 |
| 7 | 本地历史回看 | 本地图存在时不访问设备；设备离线且无图时明确显示未缓存 |
| 8 | 双 FTP 目标 | 保存配置后再启用 `new_events_only`；两个目标分别展示状态 |
| 9 | FTP 单目标离线 | 在线目标继续成功；事件展示、本地缓存和另一目标不受影响 |
| 10 | 手动历史任务 | 按 UTC `[start,end)` 创建，uploader 重启后可继续查询并执行 |
| 11 | Qt 断开 | PC 资源释放且本地数据保留；板端检测和 FTP 自动下发继续 |
| 12 | 板端重启/IP 变化 | 重新搜索后仍按 `device_id` 识别同一设备，旧本地历史可用 |

## 8. 关键风险和控制措施

| 风险 | 控制措施 |
| --- | --- |
| RTSP 解码方案过晚确定 | 第 2 天前完成目标环境 spike；同时记录 CPU、延迟、资源释放和打包依赖 |
| 三人同时改主窗口和共享模型造成冲突 | 使用服务接口和 controller 装配；共享 DTO 先评审后合入；C 负责主窗口最终集成 |
| 事件重复或状态永久停在 queued | 复合唯一键、事务 upsert、待终态集合和详情刷新四层保障，并做突发事件测试 |
| 图片损坏或留下半文件 | `.part`、长度校验、JPEG 解码校验、同目录原子改名和断开清理 |
| Token/FTP 密码泄漏 | 不提交 Git、不写普通日志、不把 Token 放 URL；密码响应只处理 `password_configured` |
| revision 冲突覆盖他人配置 | PUT 前 GET；409 后重新获取并要求用户确认合并，不自动覆盖 |
| 明文 HTTP 被误当作安全链路 | 仅允许受控局域网部署；发布说明明确 v1 不具备防抓包能力 |
| 板端限制被误归为 Qt 缺陷 | 问题单记录 API 请求/错误码/板端版本；时间持久化、自启动和保留期按外部依赖追踪 |
| 需求要求任意事件 FTP 下发 | 明确 v1 仅支持时间范围；需要精确事件列表时先走协议变更，不在客户端猜测实现 |

## 9. 单项任务完成定义（Definition of Done）

任一任务只有同时满足以下条件才可标记完成：

1. 代码已合入，接口和线程所有权清晰，没有在 UI 层直接访问 SQL 或网络 reply。
2. 正常、错误、超时、取消和断开路径均有处理；不会并发堆积同类未完成请求。
3. 新增逻辑具备自动化测试，或在无法自动化时提供可重复的真机验证步骤和记录。
4. Token、FTP 密码、Authorization 和板端绝对路径不出现在代码常量、提交内容和普通日志。
5. 数据写入满足复合键幂等；文件写入满足临时文件校验后原子替换。
6. 用户可见错误按 `error.code` 映射，不依赖英文 `message` 做业务判断。
7. 经另一名成员评审，并更新相应配置、部署或接口说明。
