# RV1126B 上位机实时视频性能评估（2026-09-28）

对象：`E:\Project\RV_CAM_APP\speeding-capture-ui`
问题：「普通电脑拉 2K 流会不会占用大量性能？以前笔记本拉 4K 会卡死，为什么？」

---

## 0. 先纠正两个前提

**前提 1：这台板子没有 4K，也没有可用的辅码流。**

| 项 | 实际情况 | 证据 |
|---|---|---|
| 传感器 | SC450AI，4MP | 板端 `production/config/vehicle_event_production.conf:111-116` |
| 主码流 video.0 | **2688×1520 @ 25fps，H.264**，min/mid/max 200/3072/6144 kbps，GOP=60 | 同上 `:120-132` |
| 辅码流 video.1 | 1920×1080，但 **`enable_venc_1=0` 强制关闭** | 同上 `:133-147` |
| 旧 3840×2160/15fps | 配置注释原文：*"was not a mode this hardware can produce"* | 同上 `:112` |
| 可用 RTSP 地址 | `rtsp://192.168.137.73:554/live/0/0`（两段式，实测 29fps） | `docs/05-链路与接口/板端对外通道清单 20260913.md:123` |

所以"拉 4K 卡死"在这块板子上不可能复现；那台笔记本遇到的是别的源。
另外：**拉辅码流不是"降低负载"的选项**——辅码流被关掉时 RTSP 会接受连接但一个字节都不发，
客户端表现为 15 秒超时后报网络错误（这正是本次修掉的 bug）。

**前提 2：硬解一直是开着的，缺的是"硬解直接上屏"。**

`main.cpp:14-17` 在未设置时把 `QT_FFMPEG_DECODING_HW_DEVICE_TYPES` 设为 `d3d11va,dx2va`，
Windows 上 Qt 6 的 FFmpeg 后端本来也只优先 D3D11VA。**解码不是瓶颈。**

---

## 1. 真正的瓶颈：每帧一次 GPU→CPU 回读 + 全幅 YUV→RGB

`src/rv1126b/infrastructure/video/QtMediaPlaybackBackend.cpp`：

```cpp
static_cast<VideoFrameWidget*>(videoWidget_.data())->setFrame(frame.toImage());
```

`frame.toImage()` 会让 Qt 走 `qffmpegvideobuffer.cpp::map()`，其中对硬解帧执行
`av_hwframe_transfer_data()`，Qt 源码注释原文是 *"retrieve data from GPU to CPU"* ——
**每帧一次 D3D11 纹理回读**，之后在 CPU 上做 YUV→RGB 全幅转换。

而且这一步跑在 **GUI 线程**（`QVideoSink::videoFrameChanged` 直连），
所以表现出来是"整个窗口卡死"，而不只是画面掉帧。

---

## 2. 实测开销（AMD Ryzen 5 9600X，ffmpeg `-benchmark`，360 帧）

单核占用率，按 30fps 折算：

| 分辨率 | 仅解码 | 解码 + RGBA 全幅转换（≈`toImage()`） | 缩小到 720p 后再转换 | d3d11va 硬解 |
|---|---|---|---|---|
| 1920×1080 | 6.4% | **19.8%** | 22.7% | 4.0% |
| 2560×1440（2K） | 10.0% | **40.9%** | 27.2% | 4.8% |
| **2688×1520（本板真实）** | 10.2% | **39.6%** | 28.9% | 4.6% |
| 3840×2160（4K） | 21.5% | **92.2%** | 50.0% | 7.8% |

- 解码算力需求：1080p@30 = 62 MP/s，2K@30 = 111 MP/s，4K@30 = 249 MP/s
- **RGB 转换比解码本身贵 2~3.3 倍**：4K 转换单项 23.6 ms/帧，超出 33ms 帧预算 2.8 倍
- 内存带宽 ~3.7 GB/s（4K@30），只占双通道 DDR4 的 5~8% —— **不是瓶颈**
- ⚠️ 口径：本机单核远强于老笔记本，笔记本按 **2~3 倍**放大；合成测试流是高熵内容，
  真实道路码流更省。所以上表是**保守上界**。

**结论（回答用户问题）**：普通电脑拉 2688×1520 一路预览，当前实现大约吃 **40% 单核**
（老笔记本 80%~120%，也就是"卡"）。**其中只有约 10% 是解码，30% 是每帧转换。**
2K 不会占满高性能电脑，但老笔记本会明显卡顿 —— 原因不是"2K 太大"，
而是这份代码把每帧都搬回内存重算了一遍。

## 3. 本次已落地的改动（低风险，不改渲染架构）

`QtMediaPlaybackBackend::handleVideoFrame`：

1. **窗口不可见时不再 `toImage()`**。最小化/被遮挡时最贵的一步直接跳过。
2. **帧信号只在真正渲染时发出**。旧写法"先无条件 `emit frameReady`，再决定要不要渲染"，
   会让上层按解码全帧率被唤醒一次；现在只在渲染/需要分辨率时发。
   注意：帧停滞看门狗另有每秒独立定时器（`checkFrameWatchdog`），不依赖本信号，
   因此这个改动不会削弱"卡流检测"。

---

## 4. 还没做、收益最大的一项（需要先验证叠加可行性）

**用 GPU 渲染路径替换 `QVideoSink + toImage()`**，例如 `QVideoWidget`（CMakeLists 已链接
`Qt6::MultimediaWidgets`），或 `QGraphicsVideoItem` + `QGraphicsScene` 把车道线 overlay
画进同一个场景。

- 预期收益：省掉每帧 4.5 ms（1080p）/ 10.3 ms（2K）/ 23.6 ms（4K）的转换与回读
- **唯一风险**：`LivePreviewPanel` 把视频输出和自绘 ARGB overlay 放在同一个
  `QStackedLayout(StackAll)` 里，overlay 还要能拖动车道线。`QVideoWidget` 在 Windows 上
  是原生子窗口，**可能永远盖在 overlay 上面**，那就不可行。
- 因此这一步必须先做叠加验证（已单独派人跑最小工程实测），验证通过才改。
  在验证结论出来之前不动渲染路径 —— 否则可能把车道线调参功能改瞎。

## 5. 其他可选优化（按性价比）

| 优先级 | 改动 | 预期 | 风险 |
|---|---|---|---|
| ★★★★ | 上述 GPU 渲染路径 | 数量级消除转换开销 | 中（原生窗口叠加） |
| ★★★ | 把 `toImage()` 放到工作线程，主线程只收 QImage | 消除"整窗卡死" | 低-中 |
| ★★★ | 转换分辨率上限（>1080p 先缩放再转 RGBA） | 2K −33%，4K −45% | 低（画质略降） |
| ★★ | `probeSize` / `networkTimeout` 提为设置项 | 只影响起播与网络 | 低 |
| ★★ | overlay 预渲染 QPixmap、局部重绘 | overlay 开销 | 低（当前实测可忽略） |
| ★ | 板端 GOP 60 → 25~30 | 降首帧延迟 | **触碰生产配置，需上板验证** |

**明确不建议**：不要再往"拉辅码流降负载"方向改（物理上没有辅码流）；
也不要打开 `enable_venc_1`（mainpath 检测模式下硬互斥，打开会让 rkipc 静默不建任何通道）。
