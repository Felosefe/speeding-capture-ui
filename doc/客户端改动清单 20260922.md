## 改动 1：事件不再因一个字段缺失而被整条丢弃

**文件**：`src/rv1126b/protocol/BoardApiCodec.cpp`

### 1a. 新增校验器（放在 `requiredBool` 之后）

```cpp
// A boolean that may legitimately be absent.
//
// Why this exists (2026-09-22, found on the board): the API copies these fields straight out
// of the event JSON and emits `null` when the key is not there -
//     out["speed_valid"] = copied_field(record.formal, "speed_valid");
// and `copied_field` returns a null Json for a missing key.  The board's own writer always
// emits speed_valid, so real events were fine; but one absent boolean made
// parseEventSummary fail, which made the client drop the ENTIRE event and show only
// "事件同步失败: Expected boolean field: speed_valid (invalid_field)".  An event that exists
// on the board and cannot be shown is worse than one shown with a defaulted field.
//
// Absent/null means "not stated", and false is the honest reading of that for both of these
// fields: speed_valid=false already means "no radar speed for this event" in the contract,
// and evidence_available=false means "no image to fetch".  A value that is present but of
// the wrong type is still an error - this tolerates absence, not nonsense.  The 0/1 integer
// form is accepted because that is what the field is called in the board's own shell tooling.
ApiResult<bool> defaultedBool(
    const QJsonObject& object,
    const char* key,
    bool fallback)
{
    const QJsonValue value = object.value(QLatin1String(key));
    if (value.isUndefined() || value.isNull()) {
        return ApiResult<bool>::success(fallback);
    }
    if (value.isBool()) {
        return ApiResult<bool>::success(value.toBool());
    }
    if (value.isDouble()) {
        const double number = value.toDouble();
        if (number == 0.0 || number == 1.0) {
            return ApiResult<bool>::success(number != 0.0);
        }
    }
    return failure<bool>(QStringLiteral("invalid_field"),
                         QStringLiteral("Expected boolean or absent field: %1").arg(QLatin1String(key)));
}
```

### 1b. 在 `parseEventSummary` 里替换两处（约第 347、354 行）

```diff
-        || !assign(requiredBool(object, "speed_valid"), &summary.speedValid, &error)
-        || !assign(requiredString(object, "speed_status"), &summary.speedStatus, &error)
+        || !assign(defaultedBool(object, "speed_valid", false), &summary.speedValid, &error)
+        || !assign(optionalString(object, "speed_status", QStringLiteral("unknown")), &summary.speedStatus, &error)
...
-        || !assign(requiredBool(object, "evidence_available"), &summary.evidenceAvailable, &error)
+        || !assign(defaultedBool(object, "evidence_available", false), &summary.evidenceAvailable, &error)
```

**注意 `requiredBool` 保持原样、其余 17 处调用不动**——这是一个刻意的决定：
`has_more` 缺省成 `false` 会让客户端**静默漏掉所有后续页**，`alive` 缺省成 `false`
会**谎报进程已死**。宽容只能用在对"缺失"唯一诚实解释的字段上。

## 改动 2：等待时间提到板端预算之上

**文件**：`src/rv1126b/network/BoardApiClient.h`（第 23-27 行）

```diff
     static constexpr int JsonConnectTimeoutMs = 3000;
     static constexpr int JsonRequestTimeoutMs = 10000;
-    static constexpr int ConfigApplyFirstResponseTimeoutMs = 15000;
-    static constexpr int ConfigApplyRequestTimeoutMs = 25000;
+    // Config apply is the one request that restarts rkipc, and the board budgets 120 s for
+    // it (kRuntimeApplyTimeoutMs in event_app_api.cc): stop the pipeline, reload, verify
+    // frames are flowing again, persist a status.  Measured on the board 2026-09-22, a
+    // whole apply took 105 s.  The previous 15 s / 25 s budget expired in the middle of a
+    // *successful* apply, so the client reported "Board connection timed out." for work the
+    // board completed - and on the line-region path that is exactly what the operator sees
+    // after pressing save.
+    static constexpr int ConfigApplyFirstResponseTimeoutMs = 135000;
+    static constexpr int ConfigApplyRequestTimeoutMs = 150000;
     static constexpr int EvidenceRequestTimeoutMs = 30000;
```

**这个"超时"不是网络问题**：客户端那个计时器从请求发出算起，到**收到响应头**才停
（`metaDataChanged`），而不是 TCP 连接超时。板端 apply 同步阻塞，实测 105 秒，
客户端 25 秒就放弃了——**板端其实成功了**。
